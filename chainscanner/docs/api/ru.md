Токен потребителя используется для подписки, чтения и подтверждения событий. Для управления узлами нужен отдельный токен администратора. В примерах используется локальный сервер из инструкции по запуску.

<a id="auth"></a>

## Подключение и аутентификация

Передавайте `Authorization: Bearer <token>` в каждом запросе. Токен определяет потребителя и его очередь. Все токены должны различаться и содержать не менее 24 байт. Маршруты управления включаются параметром `admin_token`. Для JSON укажите `Content-Type: application/json`. Успешный ответ с телом содержит JSON, ответ HTTP 204 пуст. Ошибки обычно возвращаются как обычный текст.

```sh
BASE=http://127.0.0.1:9081
TOKEN=$(jq -r '.consumers.payments' chainscanner.json)
ADMIN=$(jq -r '.admin_token' chainscanner.json)
consumer() { curl -sS -i -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' "$@"; }
admin() { curl -sS -i -H "Authorization: Bearer $ADMIN" -H 'Content-Type: application/json' "$@"; }
```

<a id="transactions"></a>

## Поиск транзакции по хешу

Передайте токен потребителя и идентификатор настроенной сети. Подписка на адрес не требуется. Ответ содержит `network`, `hash` и `result`.

Поиск по хешу отдаёт предпочтение резервным узлам и возвращает первую корректную транзакцию. Узлы, предоставившие данные при сканировании, исключаются.

HTTP 404 с заголовком `X-ChainScanner-Evidence: not_found` означает, что узел не нашёл транзакцию. Заказ можно передать на ручную проверку. При 502 или 503 повторите запрос после паузы.

При сбое запрос переходит к другому узлу. Если есть альтернативы и позволяет время запроса, выполняются как минимум три повторные попытки. Параметр `?fallback_only=true` ограничивает выбор резервными узлами. При `?observed=true` требуется сохранённый источник сканирования. Если он неизвестен или нет независимого узла, возвращается 503.

```sh
consumer "$BASE/v1/transactions/base/$TX_HASH"
consumer "$BASE/v1/transactions/base/$TX_HASH?fallback_only=true"
```

<a id="subscriptions"></a>

## Замена подписок

Передайте **полный** список подписок потребителя в виде массива JSON размером до 8 МиБ. Обязательные строки `network` и `address` задают точный идентификатор сети и допустимый в ней адрес. Пропущенные старые подписки удаляются. Пустой массив снимает все подписки, сохраняя уже поставленные в очередь события.

<a id="replace-watches"></a>

### `PUT /v1/subscriptions`

Поле `from_height` указывает первый включённый блок. В работающей сети новый адрес отслеживается со следующего блока после наибольшей назначенной высоты. При отписке `to_height` включает большую из высоты узла и наибольшей назначенной высоты. Некорректный запрос возвращает **400**. Если нужная высота недоступна, **409** сохраняет прежний список целиком.

```sh
consumer -X PUT "$BASE/v1/subscriptions" --data '[{"network":"base","address":"0x1111111111111111111111111111111111111111"}]'
```

```json
{"registrations":[{"network":"base","address":"0x1111111111111111111111111111111111111111","from_height":101}],"terminations":[]}
```

Код **202** означает, что для одной или нескольких отписок остались необработанные блоки. Повторите тот же полный список для проверки статуса. Конечная высота останется прежней. При **200** все отписки в ответе завершены: блоки подтверждены, пропуски заполнены, события помещены в очередь и доступны до подтверждения получения.

```json
{"registrations":[],"terminations":[{"network":"base","address":"0x1111111111111111111111111111111111111111","from_height":101,"to_height":110,"completed":false}]}
```

<a id="deliveries"></a>

## Чтение и подтверждение событий

<a id="next"></a>

### `GET /v1/events/next`

Обязательный параметр `network` задаёт поддерживаемую сеть. Необязательный целый `wait` включает длительный опрос на 1–20 секунд. Без него ответ немедленный. При наличии события возвращается **200**, при пустой очереди — **204**. Отсутствующая или неизвестная сеть и неверный интервал дают **400**.

```sh
consumer "$BASE/v1/events/next?network=base&wait=15"
```

В примере показано событие с сокращёнными данными транзакции. Транзакция с несколькими совпавшими адресами создаёт одну доставку на потребителя. Совпадение возможно для входящих, исходящих и неуспешных операций. Перед зачислением проверяйте направление, результат, актив и сумму.

```json
{
  "id": 17,
  "activity": {
    "confirmations": 3,
    "network": "base",
    "height": 12345679,
    "tx_id": "0xaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "time_ms": 1770000000000,
    "addresses": [
      "0x1111111111111111111111111111111111111111"
    ],
    "data": {
      "transaction": {
        "hash": "0xaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
        "to": "0x1111111111111111111111111111111111111111"
      }
    }
  }
}
```

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | `int64` | Идентификатор доставки для подтверждения. |
| `activity.network, activity.height` | `string, int64` | Конкретная сеть и позиция в реестре. |
| `activity.tx_id` | `string` | Идентификатор транзакции в сети. |
| `activity.confirmations, activity.time_ms` | `int64, int64` | Наблюдаемое число подтверждений и время в сети в миллисекундах Unix. |
| `activity.addresses` | `string[]` | Адреса из подписки потребителя, по которым найдено совпадение. |
| `activity.data` | `JSON` | Данные сети в JSON. В EVM могут присутствовать `transaction`, `logs`, `receipt` и `trace`. |
| `activity.data.refresh_assets` | `string[]` | Контракты токенов для обновления балансов после известного глобального события. Пустое поле опускается. [EVM](../guide/en.md#asset-events) |

<a id="ack"></a>

### `POST /v1/events/{id}/ack`

Укажите положительный `id` доставки в пути, тело не требуется. Подтверждение действует только для текущего потребителя и возвращает **204**, в том числе при повторе. Недопустимый или неположительный ID даёт **400**. Чтение оставляет событие в очереди. Перед подтверждением сохраните результат и исключите повторы по сети и идентификатору транзакции или перевода.

```sh
ID=17
consumer -X POST "$BASE/v1/events/$ID/ack"
```

<a id="height"></a>

### `GET /v1/heights/{network}`

Возвращает **200** и целое число JSON — наибольшую непрерывно обработанную высоту либо `-1`, если курсор отсутствует. При пропуске события с большей высотой могут уже быть доставлены. Единицы: версии реестра Aptos, слоты Solana и контрольные точки Sui.

```sh
consumer "$BASE/v1/heights/base"
```

```json
12345677
```

<a id="streaming"></a>

## Подписки в реальном времени

### От ChainScanner к приложению

Откройте WebSocket или двунаправленный поток gRPC, чтобы получать события по отслеживаемым адресам сразу после их появления в очереди. Токен, подписки и подтверждения общие с HTTP long polling. Запускайте один обработчик на пару потребитель–сеть независимо от выбранного протокола. Разные потребители могут независимо подписаться на один адрес.

**Подключение.** Выполните одну из команд в корне репозитория с токеном из раздела быстрого старта. WebSocket использует HTTP/1.1 Upgrade и текстовые кадры JSON. gRPC работает по HTTP/2 на том же порту и использует опубликованную схему protobuf. Вводите сообщения по очереди и держите поток ввода открытым. Для удалённого подключения используйте WSS или gRPC поверх TLS. Обратный прокси должен пересылать WebSocket Upgrade и потоки gRPC по HTTP/2.

[activity.proto](../../api/activity/v1/activity.proto)

```sh
websocat -H="Authorization: Bearer $TOKEN" ws://127.0.0.1:9081/v1/events/stream
```

```sh
grpcurl -plaintext -import-path . -proto api/activity/v1/activity.proto -H "authorization: Bearer $TOKEN" -d @ 127.0.0.1:9081 chainscanner.activity.v1.ActivityFeed/Subscribe
```

**Открытие → ответ.** В первом кадре укажите настроенную сеть. Передавайте полный набор адресов в `replace`, только когда меняете подписки потребителя **во всех сетях**. Пустой набор удаляет все подписки. При переподключении опустите `replace`, чтобы сохранить их. Сервер вернёт `ready`. После замены ответ содержит нормализованные адреса и начальные высоты включительно. При возобновлении список пуст.

При замене списка в потоке границы отписки приходят в `ready.terminations`. В ProtoJSON поле `toHeight` содержит десятичную строку, отсутствие поля `completed` означает false.

```json
{"open":{"network":"base","replace":{"watches":[{"network":"base","address":"0x1111111111111111111111111111111111111111"}]}}}
```

```json
{
  "ready": {
    "registrations": [
      {
        "network": "base",
        "address": "0x1111111111111111111111111111111111111111",
        "fromHeight": "12345678"
      }
    ]
  }
}
```

**Доставка → запись → подтверждение.** В каждом потоке одновременно ожидает подтверждения одна запись. Разберите исходный JSON из `dataJson` по правилам сети и сохраните результат обработки. Затем отправьте по тому же соединению `ack` с полученным ID. Следующее событие придёт, когда появится в очереди. В ProtoJSON 64-битные целые числа записываются десятичными строками. Пустая очередь не создаёт прикладных сообщений.

```json
{
  "delivery": {
    "id": "17",
    "network": "base",
    "height": "12345679",
    "txId": "0xaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "timeMs": "1770000000000",
    "confirmations": "3",
    "addresses": [
      "0x1111111111111111111111111111111111111111"
    ],
    "dataJson": "{\"transaction\":{\"to\":\"0x1111111111111111111111111111111111111111\"}}"
  }
}
```

```json
{"ack":"17"}
```

**Разрывы и ошибки.** Переподключайтесь с увеличивающейся задержкой и снова отправляйте `open`. Неподтверждённое событие может прийти повторно, в том числе по другому протоколу. Устраняйте дубликаты по сети и идентификатору транзакции или перевода. Для неверного токена WebSocket возвращает HTTP 401 при подключении, а gRPC — `UNAUTHENTICATED`. Неверная сеть или ID подтверждения приводят к коду 1008 или `INVALID_ARGUMENT`. Если начальная высота ещё неизвестна, возвращается 1013 или `FAILED_PRECONDITION`. При временном сбое хранилища — 1013 или `UNAVAILABLE`. Настройте ограничение размера входящего сообщения клиента gRPC с учётом максимального ожидаемого объёма данных транзакции.

```json
{"open":{"network":"base"}}
```

Клиент WebSocket должен отвечать кадром Pong на Ping. Используйте серверный клиент с поддержкой заголовка Authorization. Встроенный конструктор WebSocket браузера не позволяет его задать. В gRPC оставляйте канал отправки открытым для подтверждений. Чтобы остановить простаивающий поток, отмените вызов RPC. При встраивании в Go-сервер включите HTTP/2 для gRPC. В отдельном исполняемом файле уже включён HTTP/2 без шифрования на порту сервиса.

### Длинные HTTP-запросы

Приложение получает подходящие транзакции с помощью длинных HTTP-запросов. Зарегистрируйте полный список адресов и запустите по одному циклу чтения на каждую пару потребитель–сеть. Тайм-ауты клиента и прокси должны превышать `wait`. Пример использует токен из раздела быстрого старта, Python 3 и локальную SQLite. После ответа 204 сразу начинается следующий запрос. Подтверждение отправляется после записи данных.

```sh
export BASE TOKEN
python3 - <<'PY'
import http.client
import json
import os
import sqlite3
import time
from urllib.error import HTTPError, URLError
from urllib.request import Request, urlopen

base = os.environ["BASE"].rstrip("/")
headers = {"Authorization": "Bearer " + os.environ["TOKEN"]}

def request(path, method="GET"):
    req = Request(base + path, headers=headers, method=method)
    with urlopen(req, timeout=30) as res:
        if res.status != 204:
            return json.load(res)

db = sqlite3.connect("base-inbox.sqlite")
db.execute("""CREATE TABLE IF NOT EXISTS inbox (
    network TEXT, tx_id TEXT, activity TEXT NOT NULL, PRIMARY KEY (network, tx_id)
)""")
delay = 1
while True:
    try:
        delivery = request("/v1/events/next?network=base&wait=20")
        if delivery is not None:
            activity = delivery["activity"]
            with db:
                db.execute("INSERT INTO inbox VALUES (?, ?, ?) "
                           "ON CONFLICT(network, tx_id) DO NOTHING",
                           (activity["network"], activity["tx_id"], json.dumps(activity)))
            request("/v1/events/{}/ack".format(delivery["id"]), "POST")
        delay = 1
    except HTTPError as err:
        if err.code != 429 and err.code < 500:
            raise
    except (URLError, TimeoutError, ConnectionError, http.client.IncompleteRead):
        pass
    else:
        continue
    time.sleep(delay)
    delay = min(30, 2 * delay)
PY
```

Пример сохраняет для этого потребителя по одной записи на транзакцию в каждой сети. Если переводы внутри транзакции обрабатываются отдельно, добавьте в ключ дедупликации индекс перевода в сети. При потере ответа на подтверждение возможна повторная доставка. После перезапуска сканера в режиме хранения в памяти подписки и очередь теряются. Зарегистрируйте полный список заново и сверьте пропущенный интервал по своей контрольной точке и истории сети. Файловая SQLite сохраняет подписки и очередь между перезапусками.

### От узла к ChainScanner

Выберите интерфейс узла для конкретной сети. Уведомление о новой вершине цепочки запускает чтение данных. После разрыва соединения сканер восполняет пропуски по последней непрерывно обработанной высоте. Пока источник активен, поток переподключается через пять секунд. Если в сети нет отслеживаемых адресов, её сканер переходит в режим ожидания.

| Сеть | Уведомления | Источник исторических данных |
| --- | --- | --- |
| Сети EVM | WebSocket JSON-RPC · `eth_subscribe("newHeads")` | RPC уровня исполнения того же узла |
| Avalanche | Официальный WebSocket C-Chain · `newHeads` | Встроенный HTTP-узел проверяет ID сети `43114` и читает блоки и транзакции |
| Solana | WebSocket · `rootSubscribe` или поток финализированных слотов Yellowstone gRPC | HTTP JSON-RPC в `history_url` |
| Sui | gRPC · `SubscribeCheckpoints` | Чтение контрольных точек через тот же узел gRPC |
| Aptos | Поток транзакций RawData gRPC | REST полного узла в `history_url` |

```json
{
  "name": "solana",
  "protocol": "ws",
  "url": "wss://api.mainnet-beta.solana.com",
  "history_url": "https://api.mainnet-beta.solana.com"
}
```

**Ethereum Beacon (необязательно).** Узел Beacon может передавать уведомления о вершине цепочки в открытом HTTP-ответе через Server-Sent Events (SSE). Укажите `sse` в поле `protocol`, адрес `/eth/v1/events` узла в поле `url` и HTTP RPC уровня исполнения Ethereum в `history_url`. Сканер подписывается на тему `head` и сохраняет позицию по высоте блока исполнения. Узел уровня исполнения с WebSocket сам предоставляет такие уведомления.

<a id="nodes"></a>

## Управление узлами

<a id="list"></a>

### `GET /v1/admin/nodes`

Необязательный параметр `network` фильтрует список. Возвращает **200** с массивом узлов и сохранёнными результатами проверок. Запрос не расходует квоту RPC. Пустой результат — `[]`.

```sh
admin "$BASE/v1/admin/nodes?network=base"
```

```json
[
  {
    "id": 42,
    "network": "base",
    "protocol": "http",
    "url": "https://rpc.example.org",
    "origin": "custom",
    "status": "untested",
    "height": null,
    "checked_at_ms": null,
    "latency_ms": null,
    "height_unit": "block",
    "scannable": true
  }
]
```

| Поле | Тип | Описание |
| --- | --- | --- |
| `id, network` | `int64, string` | Стабильный числовой ID и конкретная сеть. |
| `protocol, url` | `string, string` | Выбранный транспорт и URL узла. |
| `origin` | `string` | Источник: `builtin`, `config`, `custom` или `chainlist`, `openchainbench`, `comparenodes`, `fallback`. |
| `status` | `string` | Одно из значений `untested`, `ok`, `timeout`, `unavailable`. Проверьте это поле после запроса. |
| `height, height_unit` | `int64? , string` | Высота узла или null. Единица: `block`, `slot`, `checkpoint`, `ledger_version` или `beacon_slot`. |
| `checked_at_ms, latency_ms` | `int64?, int64?` | Время начала в миллисекундах Unix и длительность в миллисекундах. До первой проверки оба поля равны null. |
| `read_failure, read_retry_at_ms` | `string?, int64?` | При ошибке чтения статус узла — `unavailable`. Успешная проверка высоты сохраняет причину ошибки до успешного чтения блока. На время паузы возвращается время её окончания в миллисекундах Unix. |
| `scannable` | `bool` | Может ли узел сканировать транзакции. Узлы, которые сообщают только высоту, не получают задачи сканирования. |

<a id="add"></a>

### `POST /v1/admin/nodes`

Передайте строки JSON `network`, `url` и явно укажите `protocol`. Необязательные строки: `api_key`, `history_url`, `history_api_key`. Парным транспортам нужен отдельный URL истории. Неизвестные поля, недопустимые параметры или некорректный JSON дают **400**. Допускается до 8 КиБ. При создании возвращается **201** с узлом, для существующей записи — **409**. Добавление узла само по себе не запускает сеть.

```sh
admin -X POST "$BASE/v1/admin/nodes" --data '{"network":"base","protocol":"http","url":"https://rpc.example.org"}'
```

<a id="fallback"></a>

### `POST /v1/admin/nodes/fallback`

Зарегистрируйте платный узел для чтения истории конкретной сети с теми же полями и токеном администратора, что и у обычного узла. Ответ **201** содержит `origin: fallback`. После ошибки чтения свободный резервный узел может сразу взять диапазон и проверить глубину подтверждения. Он также обрабатывает пропуски, сохранённые в SQLite до перезапуска. Новые блоки, границы подписок и обычный опрос высоты обслуживают основные узлы. Ручная проверка может расходовать квоту. Ошибки сохраняют диапазон для повтора, три ошибки подряд включают нарастающую паузу. Для проверки и удаления используйте полученный ID. Регистрируйте резервные узлы по отдельности. Пропущенные диапазоны распределяются между доступными резервными узлами.

```sh
admin -X POST "$BASE/v1/admin/nodes/fallback" --data '{"network":"base","protocol":"http","url":"https://paid-rpc.example.org","api_key":"YOUR_PROVIDER_KEY"}'
admin -X POST "$BASE/v1/admin/nodes/fallback" --data '{"network":"base","protocol":"http","url":"https://second-rpc.example.net","api_key":"SECOND_PROVIDER_KEY"}'
```

<a id="scan-progress"></a>

### `GET /v1/admin/progress`

Возвращает строку для каждой настроенной сети без запросов к узлам. `target_height` учитывает глубину подтверждения, а `cursor_height` — последняя высота, обработанная без пропусков. `lag_ms` показывает нижнюю границу времени ожидания для наблюдаемой, но ещё не обработанной высоты. При перезапуске или начале нового периода наблюдения история сбрасывается. При задержке свыше 300 000 мс статус равен `warning`, иначе `ok`. Для `idle`, `warming` и `stale` задержка равна null.

`scan_success_count` и `scan_failure_count` показывают число успешно и неуспешно обработанных диапазонов за текущий непрерывный период наблюдения. Переключение между узлами даёт один итог для диапазона. Позднейшая повторная обработка диапазона даёт новый результат. Опрос высоты, проверки узлов, простой и отменённые операции не учитываются. Оба счётчика обнуляются после завершения последней подписки или перезапуска сервиса. В старых версиях этих полей нет.

<a id="scan-retry-rate"></a>

### `GET /v1/admin/scan-retry-rate`

Требуется токен администратора. Без `network` возвращаются все настроенные сети. Пустое имя, ненастроенная сеть или повтор параметра дают **400**.

`total_attempts` считает начатые чтения диапазонов после проверки высоты узла. `retry_attempts` считает повторные чтения и попытки восстановить диапазоны, помеченные как неудачные, включая чтение с резервного узла. Попытка учитывается один раз независимо от числа высот и RPC-вызовов. Проверки высоты, поиск транзакций и повторная доставка исключены. Счётчики хранятся в памяти между периодами наблюдения и обнуляются при перезапуске службы. `retry_rate` равен `retry_attempts / total_attempts` (от 0 до 1) либо `null`, если чтений ещё не было.

```sh
admin "$BASE/v1/admin/scan-retry-rate?network=base"
```

```json
[{"network":"base","total_attempts":100,"retry_attempts":4,"retry_rate":0.04}]
```

<a id="test-one"></a>

### `POST /v1/admin/nodes/{id}/test`

Параметр пути `id` — положительное целое, тело не требуется. Ответ **200** содержит обновлённый узел даже при результате `timeout` или `unavailable`. Недопустимый ID даёт **400**, отсутствующий или удалённый — **404**.

```sh
NODE_ID=$(curl -fsS -H "Authorization: Bearer $ADMIN" "$BASE/v1/admin/nodes?network=base" | jq -er '.[] | select(.url == "https://rpc.example.org" and .origin == "custom") | .id') &&
admin -X POST "$BASE/v1/admin/nodes/$NODE_ID/test"
```

<a id="test-all"></a>

### `POST /v1/admin/nodes/test`

Проверяет все видимые узлы, с необязательным фильтром `network`. Тело не требуется. Ответ **200** содержит массив, включая неудачные проверки. Одновременно проверяется до восьми узлов. Повторный параллельный запуск группы даёт **409**. Отмена запроса останавливает проверку.

```sh
admin -X POST "$BASE/v1/admin/nodes/test?network=base"
```

<a id="delete"></a>

### `DELETE /v1/admin/nodes/{id}`

Удаляет узел по положительному `id`, в том числе встроенный или заданный в конфигурации. Возвращает **204**, при недопустимом ID — **400**, при отсутствии узла — **404**. В файловом режиме удаление сохраняется после перезапуска. Повторная регистрация адреса позволяет восстановить запись.

```sh
admin -X DELETE "$BASE/v1/admin/nodes/$NODE_ID"
```

<a id="blacklist"></a>

### Чёрный список узлов

Нужен токен администратора. Домен включает все поддомены для любых портов и сетей, IP сравнивается точно. При выборе и проверке узлов учитываются основной и исторический URL. Правила не распознают оператора за DNS-псевдонимом, прокси или глобальной конфигурацией TON.

`keyword:acme` ищет подстроку в имени узла без учёта регистра, `exact:rpc.example.org` задаёт точное имя, домен без префикса включает поддомены. Формат общий для конфигурации и обоих методов API. Пути, параметры и ключи доступа не проверяются.

```sh
admin -X PUT "$BASE/v1/admin/blacklist/keyword:acme"
admin -X PUT "$BASE/v1/admin/blacklist/exact:rpc.example.org"
admin "$BASE/v1/admin/blacklist"
admin -X DELETE "$BASE/v1/admin/blacklist/keyword:acme"
admin -X DELETE "$BASE/v1/admin/blacklist/exact:rpc.example.org"
```

GET возвращает отсортированный массив `{host, source}`. PUT и DELETE идемпотентны и возвращают 204. Правила применяются при новом выборе узлов, активный сканер обновляет пул. Файловая SQLite сохраняет изменения. Закрепите правило через `"blacklist": ["rpc.example.org"]` в корне конфигурации. При удалении такого правила API возвращает 409. Измените файл и перезапустите службу.

<a id="errors"></a>

## Обработка ошибок

Исправьте параметры перед повтором запроса с **400**. При **401** проверьте токен и его роль. Значение **409** зависит от маршрута и указано выше. **503** означает временную ошибку подписок, очереди, курсора или хранилища узлов; увеличивайте интервал между повторами. Для пустой очереди используется **204**.
