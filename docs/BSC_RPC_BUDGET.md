# BSC 按订单补扫与 RPC 用量

BSC 使用独立的实时 WebSocket 订阅与历史补扫。WebSocket 断线和重连会唤醒补扫；连接正常时仍检查有订单的区间，防止静默漏事件。其他链保持原行为。

## 调度规则

- 空闲时每 5 秒查询本地订单数据库，不持续调用 `eth_getLogs`。
- 扫描窗口从订单创建前 2 分钟开始，到原付款截止时间之后 10 分钟结束。后面的窗口仅用于收款确认兜底，不延长订单的付款期限。
- 查询包含有具体收款地址、币种和金额的链上订单；包含尚未覆盖的已过期订单和已支付订单窗口，不包含其他链、托管支付或尚未选择网络的占位订单。
- 已过期订单是否还需补扫由**已扫描区块的时间**判断，不按当前时间淘汰。停机几天后，仍会恢复尚未扫描的旧订单区间。
- 空闲时保留原扫描游标。出现新订单后，通过区块时间二分定位，跳过不含相关订单的空白区间，不根据假定出块速度跳高度。
- 每次日志查询仍最多 10 块，遵守配置的确认数和正常扫描间隔。历史追赶批次间隔 250ms。
- 区块查询、日志查询、订单查询或游标持久化失败时，不提交新的扫描进度，保留既有节点故障切换逻辑。进程重启从持久游标继续。
- BSC HTTP 节点健康探测在空闲时降至每 5 分钟一次；有待支付或近期订单时保持原有 30 秒调度。管理员手动探测不受此门限影响；本变更不改变探测方式，RPC 能力验证单独由 PR #107 处理。

## 用量边界

这主要节省没有 BSC 订单时的持续区块扫描，不能承诺一定不超过免费额度。有大量订单、长时间追赶、被反复创建订单或 RPC 持续失败时，仍可能耗尽额度。每 10 块的限制意味着持续接单时无法仅靠延长轮询间隔大幅降低日志查询总量。

已耗尽的 Alchemy 月度额度不会因代码修改立即恢复，仍需等待服务商重置或使用可用的备用节点。不要通过丢弃未扫订单区间、直接重置游标或改变付款金额匹配规则来控制预算。

## 验证与发布

本地回归覆盖空闲零日志查询、新订单唤醒、空白区间跳转、同秒多区块、过期前付款恢复、过期后付款拒绝、重启重放去重、RPC/数据库错误、确认数与落后节点。

```sh
cd src
go test ./task ./model/data ./model/service
go test -race ./task -run 'TestBsc' -count=1
```

发布前需通过仓库 CI、记录原镜像和运行配置；发布后观察实际 RPC 用量及小额订单识别/回调。代码测试不等于生产支付验证。本变更不新增数据库表或修改订单记录。
